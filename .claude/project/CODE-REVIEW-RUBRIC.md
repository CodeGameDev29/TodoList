# Code review rubric

Version 1, researched 2026-10-07. This is the review contract for this repository's JavaScript React SPA, Node.js/Express API, SQLite storage, Python harness, and supporting files. Read it before every independent code review. Recheck the primary sources when changing language versions, framework behavior, or these rules.

## Decision process

Review formatting and indentation first, then human readability, correctness, robustness, and verification. A formatting pass does not establish correctness. Do not offset a correctness defect with good style or use an invented numerical quality score.

For every applicable rule below, record `PASS`, `FAIL`, or `NOT_APPLICABLE`, with file/line or captured-check evidence. Explain every nonapplicable rule and coverage exclusion. Unrun required checks are `FAIL` with an evidence-gap explanation, not assumed passes. Group equivalent findings under one bug class while listing affected surfaces.

Each finding must identify its rule IDs, severity, bug class, location, concrete trigger or source evidence, effect, and smallest useful correction. Use P0 for immediate severe loss/exposure, P1 for major broken behavior, P2 for normal defects or required formatting/readability failures, and P3 for nonblocking suggestions. A preference without a rule violation and a concrete benefit is not a defect. The orchestrator classifies findings before fixes; a separate reviewer verifies changes. The review author must not edit, rerun checks, or approve deployment.

## Design and coding paradigms

Apply these principles in the context of this small application; do not treat a named pattern as a requirement to add more code.

- **JavaScript modules and composition:** prefer focused ES modules and functions. Use classes only when an object with state and a lifecycle makes the code clearer. Keep input validation, domain operations, and persistence responsibilities understandable. Dependency injection of the repository and clock makes behavior testable without a large framework. These are project applications of READ-01 and TEST-01.
- **Declarative React:** derive the UI from state, keep state as small as practical, and preserve one-way data flow. Separate render calculations from event handlers and effects. Extract components when they clarify a responsibility, not to meet an arbitrary file-length limit. See [Thinking in React](https://react.dev/learn/thinking-in-react); apply REACT-01/02 and READ-02.
- **Python's explicit procedural style:** use named functions, straightforward branching, context managers for resource lifetimes, and exceptions with useful context. Avoid compressed statements, hidden global mutation, and inheritance introduced only for a pattern. PEP 8 and PEP 20 inform PY-01/02 and READ-01.
- **Declarative SQL with explicit boundaries:** express filtering and ordering in queries, bind data values, and use transactions where operations must succeed together. Keep schema constraints and service validation complementary. Apply DATA-01/02.
- **Practical simplicity and reuse:** remove duplication when it represents the same changing rule, but preserve necessary independent validation at browser and server trust boundaries. Prefer a small cohesive solution over speculative extensibility. Reviewers must explain the concrete benefit of any proposed abstraction using READ-01, API-01, and TEST-01.

## Formatting and readability

These exact conventions are project decisions, not universal language requirements. Prettier preserves syntax semantics while applying a consistent layout; its print width is a wrapping target, not a strict maximum. Python uses Ruff's formatter, with PEP 8 as the human-review reference. [Prettier rationale](https://prettier.io/docs/rationale), [Ruff formatter](https://docs.astral.sh/ruff/formatter/), [PEP 8](https://peps.python.org/pep-0008/).

| Rule    | Required standard                                                                                                                                                                                                                                                                                                        | Review evidence                                                                                |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| FMT-01  | Pinned formatter checks pass for maintained JS/JSX, CSS, HTML, JSON, YAML, Markdown, and Python. Changes must not alter behavior merely to satisfy layout.                                                                                                                                                               | `npm run format:check` output and diff review.                                                 |
| FMT-02  | Use spaces: two for web/configuration files and four for Python. JS uses semicolons, single-quoted strings, and Prettier's 100-column target; JSX attributes remain double quoted. Python uses Ruff's 88-column target. Use UTF-8, LF, and a final newline; Windows `.cmd` wrappers use CRLF. Avoid trailing whitespace. | Formatter output, `.editorconfig`, manual checks for unsupported formats.                      |
| FMT-03  | Visually expose block structure: separate JSX siblings, CSS declarations, and Python compound statements. Do not compress unrelated actions onto one line. Format small SQL, TOML, Dockerfile, shell, and command wrappers consistently by inspection where no formatter applies.                                        | Representative diffs and inspection of each unsupported format.                                |
| FMT-04  | Format canonical sources, then regenerate mirrors. Never format generated mirrors independently. Exclude dependencies, build outputs, user IDE files, data, secrets, and run artifacts; validate lockfile and mirror integrity separately.                                                                               | Formatter file scope, synchronization check, lockfile install.                                 |
| READ-01 | Names should explain domain meaning and units; functions/components should have a clear responsibility. Prefer straightforward control flow and cohesive route/service/repository boundaries. Do not mandate classes, design patterns, or extra abstraction without a concrete benefit.                                  | Trace a request and a task mutation through named functions.                                   |
| READ-02 | Break dense conditional rendering or deeply nested logic into readable branches or focused helpers when formatting alone is insufficient. Avoid arbitrary line-count limits and speculative rewrites.                                                                                                                    | Explain each loading/error/empty/success branch without reconstructing compressed expressions. |
| READ-03 | Comments explain nonobvious intent or tradeoffs; remove stale claims and avoid narrating obvious assignments. Explain deliberate exceptions, including synchronous SQLite, UTC dates, and ASCII title ordering.                                                                                                          | Comments and documentation agree with actual behavior.                                         |

The emphasis on explicit, simple, readable code follows the design guidance in [PEP 20](https://peps.python.org/pep-0020/). JavaScript naming, declarations, and block-style checks are informed by [MDN's JavaScript example guidelines](https://developer.mozilla.org/en-US/docs/MDN/Writing_guidelines/Code_style_guide/JavaScript); MDN's documentation-specific choices are not all imposed on this application.

## JavaScript and React

| Rule     | Required standard                                                                                                                                                                                                             | Review evidence                                                             |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| JS-01    | Prefer `const` unless reassignment is needed, explicit comparisons, descriptive camelCase functions/variables, and PascalCase React components. Avoid implicit globals and unnecessary coercion.                              | Source inspection; justify local exceptions.                                |
| JS-02    | Handle asynchronous failures and cleanup deliberately. Await operations whose completion matters; distinguish a confirmed write from a subsequent failed refresh. Do not silently convert failures into success.              | Success/failure paths and relevant regression tests.                        |
| REACT-01 | Keep rendering pure, update state immutably, call hooks at component/hook top level, and use stable task IDs as list keys. Keep event-driven work in handlers.                                                                | Render/state inspection and component tests.                                |
| REACT-02 | Effects declare their reactive inputs and clean up requests. Prevent obsolete reads from replacing current state. Inspect real fetch/abort behavior before alleging a race; a hypothetical mock-only failure is insufficient. | Effect dependencies, cleanup, stale-result tests and user journey evidence. |
| REACT-03 | Forms and controls have accessible labels, keyboard access, visible focus, understandable validation, and distinct loading/error/empty states. Do not erase drafts on failed writes.                                          | Semantic markup, tests, headed browser evidence where behavior changes.     |

React's purity and effect lifecycle rules support REACT-01/02, including cleanup for out-of-order responses. Stable keys associate list items with their data. [React purity rules](https://react.dev/reference/rules/components-and-hooks-must-be-pure), [useEffect](https://react.dev/reference/react/useEffect), [list rendering](https://react.dev/learn/rendering-lists).

## Node.js, Express, and persistence

| Rule    | Required standard                                                                                                                                                                                                     | Review evidence                                                 |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| API-01  | Validate untrusted bodies and query values at the boundary; reject unknown/invalid inputs consistently. Keep public HTTP methods, statuses, errors, defaults, and serialization aligned with the acceptance contract. | API tests, route/service/validation trace.                      |
| API-02  | Preserve Express error middleware's four-argument signature; forward errors appropriately and avoid writing after headers are sent. Return useful client errors without exposing server internals or secrets.         | Middleware inspection and failure tests.                        |
| DATA-01 | Bind data parameters; whitelist any SQL identifiers/directions. Preserve existing rows, migrate transactionally, and close resources. Handle nulls, date boundaries, and deterministic ordering explicitly.           | Repository/migration inspection and isolated integration tests. |
| DATA-02 | Tests and smoke scripts use isolated data and narrowly scoped cleanup. Production/default development data must not be fixtures. Account for synchronous SQLite's limited concurrency in stated tradeoffs.            | Database paths, unique resource names, preservation evidence.   |

Express documents error-handler signatures and forwarding behavior. Node's SQLite documentation describes prepared statements, binding, transactions, and synchronous database access. [Express error handling](https://expressjs.com/en/guide/error-handling/), [Node 24.15 SQLite](https://nodejs.org/download/release/v24.15.0/docs/api/sqlite.html). The detailed validation and migration acceptance rules are this project's choices.

## Python harness and operational files

| Rule       | Required standard                                                                                                                                                                                                                                                    | Review evidence                                                            |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| PY-01      | Follow PEP 8 naming, four-space indentation, separated imports, sensible blank lines, and one statement per line. Prefer explicit readable branches over packed expressions. Ruff formatting is the layout authority; human review still covers names and structure. | Python formatter check and source inspection.                              |
| PY-02      | Use deliberate file encodings and portable paths; preserve diagnostic context and distinguish expected failures from programming errors. Bound external commands where a hang would block automation.                                                                | I/O/subprocess paths and failure-path tests.                               |
| HARNESS-01 | Validate untrusted reports, paths, roles, and state before recording success. Require independent identities and evidence, read-only review roles, and canonical/generated agreement.                                                                                | Validator, report/ledger tests, synchronization and semantic role loading. |
| OPS-01     | Container builds separate build/runtime dependencies, use a non-root runtime, preserve data in a volume, and keep local secrets/artifacts out of the build context. Bind local demos to loopback.                                                                    | Dockerfile/context/Compose review and actual runtime smoke evidence.       |
| OPS-02     | Pin development tools reproducibly, keep their checks in CI, and avoid unrequested machine-wide changes. Cleanup must target only owned temporary resources.                                                                                                         | Lockfiles, CI, install/run/cleanup scripts.                                |

Python conventions draw from [PEP 8](https://peps.python.org/pep-0008/); Ruff's explicit configuration controls formatter scope. Container structure follows Docker's guidance on multi-stage builds, limited dependencies, context exclusions, and runtime users. [Ruff configuration](https://docs.astral.sh/ruff/configuration/), [Docker build guidance](https://docs.docker.com/build/building/best-practices/).

## Tests, documentation, and final review

| Rule      | Required standard                                                                                                                                                                                                           | Review evidence                                                 |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| TEST-01   | Verify externally meaningful behavior and boundary/failure cases. Reproduce confirmed behavioral defects before fixing and retain focused regressions. Avoid tests that merely duplicate implementation details.            | Named tests linked to acceptance and findings.                  |
| TEST-02   | Evidence corresponds to the reviewed revision/files and covers affected behavior. A prior green run is context, not proof of new changes. Formatting-only edits still require appropriate tests/build checks.               | Revision or source hashes, command logs, independent judgments. |
| DOC-01    | Setup, test, formatting, architecture, scope, and assumption documentation reflect the current repository. Commands and referenced paths must exist. Explain necessary local prerequisites and known limitations.           | Documentation/path inspection and relevant command results.     |
| REVIEW-01 | Inventory all first-party surfaces, explicitly account for generated/dependency files, and map findings to this rubric. State coverage gaps and unresolved findings; do not promise that review proves absence of all bugs. | Final coverage inventory and per-rule assessment.               |

Testing and review gates above are project policy. They translate the user's interviewer-focused quality requirement into checkable evidence; they do not claim to be universal requirements of a language or framework. Never expand review scope into authentication, multi-user behavior, or additional product features without the user's instruction.
